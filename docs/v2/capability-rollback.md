# Native capability rollback and diagnostic suspension evidence

Updated October 11. This closes the assigned helper/transaction mechanisms,
not the full lifecycle, learned tool capability, or v2 release goal.

## RAM first, authorized storage fallback

`CapabilityRollbackSnapshot` is shared by canonical and connected capability
rehearsal. It holds the actual registered packed signs, integer connection
state, repeated-contact pages, row resistance, native byte controls, counter
key sets, pending stability events, and mixed training modes. No full floating
weight model or floating learned master is created.

The snapshot first reserves compact CPU state. If that reservation is refused,
it may use a private bounded safe-tensor snapshot only when the instance has
enabled disk-state offload, an owned cache directory exists, and its resource
policy admits the disk allocation. It retains a small admitted transfer peak
for restoration rather than requiring a second whole-head allocation. Shared
spill leases charge the real owned file until deletion. Unavailable RAM and
unauthorized/refused storage stop the transaction before learning mutates it.

When storage directories are selected, fallback calls the existing
`allocate_spill_file` path using an internal `.packed-rollback` file. Actual
local picker grants, selected physical-drive quotas, rate ordering and reserve
watermarks govern placement. A full faster selected drive can use another
authorized selected drive; an ungranted path cannot fall back to the primary
cache. No selected directory preserves the existing single-drive path. Only
registered generated rollback files from verified dead jobs qualify for stale
drive-cache cleanup. Durable diagnostic exports remain checkpoint authority
on their caller-owned instance path, not ephemeral cross-drive caches.

Both successful and declined rehearsal candidates close their private
snapshots. Failed/declined candidates restore real pre-candidate native bytes,
topology, controls, counters, events and modes. Generic maintenance still does
not overwrite independently grounded route/argument owners. These receipts do
not certify that the brain is competent at the declared tools.

## Durable net-delta baseline

`ParameterDeltaJournal.export_resume_state()` writes a sealed baseline bound
to the caller-verified neural checkpoint/turn identity. It stores only changed
first-original byte positions, explicit small control baselines, named owner
bindings, sparse implicit-zero births, and repeated-contact topology
boundaries. It does not copy the neural model. The active journal remains live
until the surrounding suspension record commits.

`from_resume_state()` validates the manifest and every file hash, named class,
shape/dtype, original sparse offset, representation flag, birth owner and
topology boundary before registering a mutable diagnostic observer. It binds
the loaded owners rather than taking their current values as a new baseline.
Later writes/reversals and exact rollback therefore retain the original
turn's net-delta semantics across cold owner recreation.

Persistent byte-valued controls, including row resistance, are preserved as
controls rather than interpreted as ternary sign lanes. Explicitly
nonpersistent sort caches are excluded. A post-publication quota failure
removes only the exact newly created diagnostic directory and releases the
attempt's leases; it does not close or alter the original live journal.
Successful exported files retain their shared-pool charges while present.

The native lifecycle owner is separately integrating these APIs through
`ExecutionCheckpointStore` and the same-turn worker/controller. These helper
tests alone do not establish whole-app unload/resume or external-handle
reconnection.

## Focused verification

- Four existing rollback, ten journal-resume, and ten selected-modality cases
  passed together: 24 cases in 6.134 seconds. The scope includes actual native
  heads/tables, canonical replay, CPU/Metal and two-rank collective mechanisms;
  no user model or corpus was initialized.
- Two new reproductions first exposed a nonpersistent-sort/control-byte
  inventory failure and an unreceipted published directory after a final
  quota error. Both passed after the targeted fixes (0.055 seconds).
- Two additional cases passed in 0.249 seconds: real shared-pool file charging
  and cleanup, plus connected replay's authorized storage fallback followed by
  exact rollback of an interrupted native candidate. Connected capability
  measurements are stubbed in this transaction fixture; its actual native
  packed owners are not stubbed, and no tool-quality conclusion is drawn.
- The affected diagnostic/resume suites then passed 28 cases in 0.290 seconds,
  including primitive original-byte reversals, paging replacements, refusal,
  exact retry rollback, real native-table learning/reload/restore, sparse
  births, repeated-contact rollback, observer/owner lifetime, and file charges.
- Two selected-drive cases passed in 0.131 seconds. After adding an
  after-write failure injection, all seven capability rollback cases and one
  affected stale-drive cleanup case passed in the follow-up run. Two pager
  selectors initially named the wrong unittest class and did not execute;
  the corrected exact cases both passed separately. This was a test-command
  naming error, not a runtime failure. Selected placement used real small
  files and ledger grants with injected two-volume free-space readings, not
  two separate physical disks.
- Three affected slow-integrity snapshot cases passed in 0.019 seconds,
  covering bounded writes, byte-control rollback and nested snapshot lifetime.

Tests live in `test_capability_rollback.py`,
`test_connected_capability_transaction.py`, `test_parameter_journal_resume.py`,
and `test_parameter_diagnostics.py`. The related two-axis table evidence and
bounded performance comparison are in `weighted-modalities.md`.

## Remaining boundaries

These are admission and owned-file accounting mechanisms, not OS-enforced RSS
isolation or pinned physical RAM. Actual CUDA/NPU/multi-GPU parity, large-head
rollback I/O latency, full same-turn cold app resume, broad retention, trained
quality, cross-platform packages and CI/release remain separate gates. No
full user-corpus training, commit, CI job or release was performed here.
